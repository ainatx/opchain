## Executive Summary

The core guarantees hold. In every run, including ones built to break it, the scan printed only path, commit, line and rule id. No repository setting, hook or attribute ran anything. No git transport opened a connection. Every NOT-CHECKED outcome was a non-zero exit, and the private folder was gone after every exit other than SIGKILL. The builder's private bare copy is the right route (verdict below), and the git status wrapper is a real find: gitleaks does report "no leaks" on a broken history, and the wrapper turns each case I tried (missing commit, tree or blob) into `scan-failed`.

The weak spot is **completeness: when the scan may say CLEAN**. gitleaks' git mode has defaults and built-in allowlists that ow-tools inherits but doesn't state, and the claims are written as absolutes:

1. **SS-01 (MEDIUM): a type change is filtered out.** `--diff-filter=tuxdb` (gitleaks' default, kept in `LOG_OPTS`) drops `T` pairs, so a key in a file that replaced a symlink (a shared settings file brought into the repository) is never read: CLEAN. One-line fix, verified: `--diff-filter=uxdb`.
2. **The repository can still steer the scan by naming** (SS-02). gitleaks' built-in global allowlist is path-based. A key under any path containing `gitleaks.toml` (the regex is unanchored), `node_modules/`, `venv/lib/`, or in a `.pdf`-named text file is never reported. This contradicts "the repository can't steer it" and "can't switch the scan off".
3. **History and content the claims cover, or the residuals don't name, are not read** (SS-03, SS-04): an octopus evil merge, older stash entries, refs that point straight at a blob, `ORIG_HEAD`/`FETCH_HEAD`, submodule histories, NUL-byte and UTF-16 files, and commit and tag messages.
4. **Claim accuracy** (SS-06, SS-07, SS-08):
   - The scan does write to the client's repository: git refreshes pack timestamps through the alternates.
   - Committed text does reach the private folder, zlib-compressed, as git's remerge objects. The shipped proof greps raw bytes, so it can't see them.
   - A secret in a path is printed. That residual is stated, but three texts say the scan never prints a secret.

**Grade: B+.** It would be A− once SS-01 is fixed and the claims and residuals in SS-02 to SS-08 are corrected.

## Findings

### [SS-01] A type change is filtered out: a key in a file that replaced a symlink is CLEAN

**Risk:** MEDIUM · **Category:** integrity (false CLEAN) · **Where:** `plugins/ow-tools/lib/scan-secrets.mjs:31-34` (`LOG_OPTS`, `--diff-filter=tuxdb`); design §5.5 "How", §16.2 item 4 · **Fix effort:** XS

**Problem:** gitleaks' default `--diff-filter=tuxdb` excludes type changes (`t`). When a tracked symlink becomes a regular file, git records `T`, and the whole file pair is filtered out, so the new file's lines never reach gitleaks. This happens by accident. A repository that once linked `config/secrets.ini` to a shared file (a common deploy pattern), and later committed the real file, gets CLEAN.

**PoC (`SS-01`):** commit a symlink `secrets.ini → ../shared/secrets.ini`, then replace it with a file holding a fake AWS key. `git show --name-status` reports `T secrets.ini`. ow-tools: exit 0, **CLEAN**. Control: the same key in an ordinary file gives HITS. Plain gitleaks in place: "no leaks". With `--diff-filter=uxdb`: "leaks found: 1".

**Fix (verified on a copy of the plugin):** `LOG_OPTS` → `--diff-filter=uxdb`. gitleaks reads added lines only, so the deleted symlink target adds nothing. In the patched copy, symlink → file gives HITS (`secrets.ini`, line 1, `aws-access-token`), and file → symlink adds no extra row. Update §5.5, §16.2 and the regenerated manifest. Add `SS-01` to `FIXED`.

### [SS-02] gitleaks' built-in global path allowlist lets a repository hide a key by naming its path

**Risk:** LOW (deliberate, or rare accidental) · **Category:** repository-controlled behaviour (item 4) · **Where:** `GITLEAKS_CONFIG` (`[extend] useDefault = true`), `scan-secrets.mjs:63`; claims in design §5.5 "The repository can't steer it", README "can't switch the scan off", `IGNORED` · **Fix effort:** S (residual) / M (own config)

**Problem:** gitleaks 8.30.1's default config carries a global `[allowlist] paths` list that `useDefault` brings in. It includes an unanchored `gitleaks\.toml`, `(?:^|/)node_modules(?:/.*)?$`, `(?i)(?:^|/)(?:v?env|virtualenv)/lib…`, lock files, `vendor/(bundle|ruby)/`, `.gem`, and image, font, office and `.pdf`/`.bin`/`.exe` extensions. A repository that names a folder `gitleaks.toml/` hides every key in it. This is the same class as the `.gitleaksignore` route the builder closed.

**PoC (`SS-02a`–`e`):** a fake AWS key in `gitleaks.toml/prod.env`, `deploy/ci-gitleaks.toml.env`, `app/node_modules/settings/.env`, `venv/lib/settings.py` and a text file `credentials.pdf`: each **CLEAN**. Control: the same key as `settings.ini` gives HITS.

**Fix (OWNER-DECISION OD-1):**
- **(a)** State the built-in path allowlist as a residual in §16.3 and in the `CLEAN` note, and qualify the README and §5.5 claims ("can't switch the scan off" becomes "its own allowlist files, config and attributes are not used; gitleaks' built-in allowlist still skips some paths, for example dependency folders, lock files and binary formats").
- **(b)** Ship ow-tools' own copy of gitleaks' rules without the global `paths` list, generated from the pinned gitleaks version by a script. That means more findings in vendored code, and a file to follow on each gitleaks upgrade.

I recommend (a) for 1.3.0 and (b) for consideration in v2.2.

### [SS-03] History the claims cover, or the residuals don't name, is not scanned

**Risk:** LOW · **Category:** integrity / claim accuracy · **Where:** `buildMirror` (`scan-secrets.mjs:428-462`), `note` (`:615-619`), design §5.5 "What it scans", §16.3 · **Fix effort:** S (state) / M (code)

| Sub | Route | Result | Claim it contradicts |
|---|---|---|---|
| a | A key added only in an **octopus** merge (3 parents, amended) | CLEAN: `--diff-merges=remerge` shows nothing for octopus merges | "merges included" (§5.5, README) |
| b | A key in **`stash@{1}`** (an older stash) | CLEAN; `stash@{0}` alone is found | "every ref (… the stash)" (§5.5). Older entries are reflog-only |
| c | A ref straight to a **blob** (`refs/keep/settings`) | CLEAN with `refs: 3`: copied, but `git log --all` skips non-commit refs | "every ref" |
| d | A commit reachable only from **`ORIG_HEAD`** (after `reset --hard`), or only from `FETCH_HEAD` | CLEAN | §16.3 names reflogs, worktree HEADs and unreachable objects only |
| e | Commits present but **no ref left** | CLEAN, `refs: 0`, note "The repository has no commits" | The note is false: the objects are there |
| f | A **submodule**'s history | Superproject: CLEAN. Submodule folder: `repo-not-contained` "…scan the repository it belongs to", which doesn't cover it. `.git/modules/<name>`: HITS | Not stated anywhere |

**Fix:**
- Add a–f to §16.3.
- Change the `refs: 0` note to "no refs, so nothing in the history is reachable to scan".
- For a submodule (a `.git` file pointing into a parent's `.git/modules/`), name `<superproject>/.git/modules/<name>` in the refusal, and list `.git/modules/*` as "not scanned" in a superproject's result.

Optional code:
- copy `refs/stash` reflog entries as extra refs (read `logs/refs/stash` as text, or `git log -g --format=%H refs/stash` under the hardened environment);
- a second gitleaks pass with `--min-parents=3 --diff-merges=separate` for octopus merges.

Pushed history (what the client receives) is the part that matters most, which is why b, d and e are LOW. a and c can be pushed.

### [SS-04] Content gitleaks' git mode never reads: binary-looking files, commit and tag messages

**Risk:** LOW · **Category:** integrity / claim accuracy · **Where:** `LOG_OPTS`; design §16.3 · **Fix effort:** S (state) / M (`--text`)

**Problem:** git treats a file with a NUL byte in its first 8,000 bytes as binary, so `log -p` prints "Binary files differ" and gitleaks reads nothing. That covers UTF-16 text: Windows PowerShell 5.1's `>` writes UTF-16LE, so an `.env` made that way is a real accidental case. gitleaks' git mode also never reads commit or tag messages.

**PoC (`SS-04a`–`c`):** a NUL byte before the key, a UTF-16LE `.env` with a BOM, and a key in a commit message and an annotated tag message: each **CLEAN**. In place with `--log-opts="--all --text"`, gitleaks finds the NUL case.

**Fix (OWNER-DECISION OD-2):**
- **(a)** State it in §16.3 and in the CLEAN note ("binary and UTF-16 files, and commit messages, are not read").
- **(b)** Add `--text` to `LOG_OPTS`, at the cost of diffing every real binary as text. That means slower scans, very long lines (tested fine up to 12 MB) and possible noise.

I recommend (a), plus a CLEAN note that names the gap.

### [SS-05] Binary lookup trusts PATH folders the repository can control

**Risk:** LOW (needs the operator's PATH to hold a folder inside the repository, or a relative entry) · **Category:** code execution from repository content (item 3) · **Where:** `findOnPath`/`versions`/`requirements` (`scan-secrets.mjs:99-119`), called at `:528-529` **before** `inspectRepo` (`:531`); `doctor.mjs:147,151` (`which` + bare-name `versionOf`) · **Fix effort:** S

**Problem:**
- **(a)** `findOnPath` drops relative entries but trusts any absolute one, including a folder inside the repository being scanned. direnv's `PATH_add bin`, an activated `.venv` and `node_modules/.bin` under `npm run` all add one. The `git --version`, `gitleaks version` and `gitleaks git --help` probes run before the repository is even inspected.
- **(b)** `doctor` and `version --json` still find `gitleaks` and `git` through relative and empty PATH entries and run them by bare name from the current folder. `version --json` is how ow-handoff tells whether the scan is ready, and it reports `scan-secrets: ready` on a binary that `scan-secrets` itself refuses to use.

**PoC (`SS-05a`, `SS-05b`):**
- (a) PATH = `<repo>/bin:…` with marker-writing `gitleaks` and `git` in `<repo>/bin`: the marker records `git --version`, `gitleaks version` and `gitleaks git --help`.
- (b) cwd = the repository, PATH = `.:…`: `doctor --json --quick` and `version --json` each run `./gitleaks version` and `./git --version` (marker), and report `{ ready: true }`.
- An empty PATH entry for `scan-secrets` was correctly ignored (no marker; the real gitleaks ran).

**Fix:**
- Inspect the repository first.
- Refuse (`repo-not-contained` or a new `scanner-untrusted`) a gitleaks or git whose real path, or whose PATH folder, is inside the repository root or its git folder. Optionally also refuse one in a group- or world-writable folder.
- Make `doctor` use `findOnPath` and run the absolute path for the `gitleaks` and `git` rows. Ideally do the same for every tool row; that is pre-existing for ffmpeg and the others.
- Correct §16.2 item 12, which says doctor's probes "keep the 1.0.0 lookup".

### [SS-06] The scan changes the client's repository: git refreshes its object timestamps

**Risk:** LOW · **Category:** claim accuracy (writes into the client repository) · **Where:** `--diff-merges=remerge` through `objects/info/alternates` (`scan-secrets.mjs:443`); manifest Files row "Nothing is written in the scanned repository"; §16.1 · **Fix effort:** S (state)

**Problem:** remerge-diff re-creates merge results. When an object it writes already exists in an alternate, git freshens it there (`utime` on the source's pack file or loose object) instead of writing a copy. No bytes or files are created in the repository, but its timestamps change.

**PoC (`SS-06`):** a clean `--no-ff` merge, `git gc`, every file under `.git/objects` set to 2020-01-01. After the scan (CLEAN), the `.pack` file's mtime is now. Lab: the `stat` diff of `.git` shows exactly one changed entry, the pack.

**Fix:** git has no switch for this. In the manifest and §16.1, replace "Nothing is written in the scanned repository" with "No file in the repository is created or changed; git may refresh the timestamps of its pack and object files (it freshens objects a merge re-creates)". Add it to §16.3.

### [SS-07] Committed text reaches the private folder, compressed, and the redaction proofs can't see it

**Risk:** LOW · **Category:** residue / proof method · **Where:** `history.git/objects/tmp_objdir-remerge-diff-*` inside the private folder; §16.3 SIGKILL residual ("…never a match"); `leaksInFiles` and `realWrapper` in `tests/ow-tools/scan-secrets.test.js` · **Fix effort:** S

**Problem:** remerge-diff writes each re-merged blob into a temporary object folder inside the copy, in the private folder. A conflicted side that added a key is re-written there, conflict markers and all. These are zlib-compressed git objects. git removes them when it exits, so a normal run, a timeout and every handled signal leave nothing. But:

- If git itself is killed outright (the whole tree SIGKILLed, the OOM killer, a power cut), the leftover folder can hold key text. §16.3 says such a leftover holds "never a match".
- The shipped proof copies the folder after gitleaks exits, when the objects are already gone, and greps raw bytes (latin1). A compressed object never matches a 12-character window.

**PoC:**
- `SS-07a`: a git object holding a key has no window in its raw bytes and has the key once inflated.
- `SS-07b` (300 merges in the PoC; 400 in the lab run quoted here): each merge conflicts with a side that added the key. A poller copying `tmp_objdir-*` while the scan ran caught 231 files, **150 held a key window once inflated, 0 raw**. The folder was gone at the end.

**Fix:**
- Correct §16.3 and the manifest's Files row ("…and git's temporary merge objects, which can hold committed text, compressed").
- Make the proof inflate any zlib stream it finds (a git loose object), and snapshot during the run as well as at the end.
- Optionally add `GOTRACEBACK=none` to gitleaks' environment (residual below).

### [SS-08] A secret in a file or folder name is printed, and three texts say the scan never prints one

**Risk:** LOW (residual stated, but the claims are absolute) · **Category:** redaction (items 1–2) · **Where:** `.File` in the template, `ROW` (`scan-secrets.mjs:72`); README line 51 "never what it is"; `/ow-tools` SKILL line 36 "prints or stores … a secret a scan found"; `cli.mjs:37` "never prints a credential" · **Fix effort:** S (claims) / M (masking)

**Problem:**
- §16.3 states that a path holding a secret is printed, and the contract allows that as a stated residual.
- A path-only rule (`pkcs12-file`) reports a file whose name is itself the token, with no content needed.
- These rows flow into ow-handoff's `accounts.md` (Part 2's concern).

**PoC (`SS-08`):** a fake GitHub token as a folder name (`keys/<token>/creds.ini`, AWS key inside) appears verbatim in the JSON `rows[].path` and in text mode. `<token>.p12` → `pkcs12-file`, token printed.

A token in a branch name or commit message did **not** appear in any output (0 windows, JSON and text).

**Fix (OWNER-DECISION OD-3):**
- **(a)** Qualify the three claims ("never prints the matched text; a path that is itself secret is shown as it is").
- **(b)** Also mask: pass the unique row paths through `gitleaks stdin` with the same config and template, and replace any path segment that matches with `<withheld: matches rule-id>`.

I recommend (a) now and (b) as cheap hardening.

### [SS-09] Refs whose names differ only in case can never be scanned on a case-insensitive volume

**Risk:** LOW (availability; fails safe) · **Category:** robustness · **Where:** `buildMirror` `update-ref --stdin` with the source's ref names (`scan-secrets.mjs:446-453`) · **Fix effort:** XS

**Problem:** the copy writes loose refs under their own names. On APFS (case-insensitive by default), `refs/heads/Secret` with `refs/heads/secret`, or `refs/heads/A` with `refs/heads/a/b`, collide, so the transaction fails. That is common enough in repositories from Linux teams, and every scan of such a repository is NOT-CHECKED with no workaround.

**PoC (`SS-09`, skipped on case-sensitive volumes):** packed refs `refs/heads/Secret` (the key) and `refs/heads/secret` → exit 5, "git could not copy the refs". The same for `A` with `a/b`.

**Fix:** write each ref into the copy as `refs/ow/<n>`. `--all` doesn't care about names. This also keeps branch names, which can themselves hold secrets, out of the private folder. Alternatively, `git init --ref-format=reftable` for the copy.

### [SS-10] The partial-clone pre-check reads two spellings only

**Risk:** INFO (fails safe, no connection) · **Where:** `partialClone` (`scan-secrets.mjs:241-249`) · **Fix effort:** XS

**PoC (`SS-10`):** a missing blob, `promisor = 1`, and `extensions.partialClone` in an `include.path` file. The text check misses all three. Plain git in place connects to the listener (control: 1 connection). ow-tools: **0 connections**, NOT-CHECKED, but `scan-failed` instead of `history-incomplete`, so the next step it gives is the less useful one.

**Fix:** match git's boolean spellings (`true|yes|on|1`), or ask git (`git config --get-regexp '^(extensions\.partialclone|remote\..*\.promisor)$'`, include-aware, under the hardened environment). Map a "missing object" from the wrapper's failed `log` to `history-incomplete`.

### [SS-11] Containment stops at `.git`: `packed-refs`, `refs/` and `objects/` can point outside the folder

**Risk:** INFO · **Where:** `inspectRepo` (`scan-secrets.mjs:189-239`) · **Fix effort:** S

**PoC (`SS-11`):** `.git/packed-refs` is a symlink to a file outside the folder. It is read; the scan proceeds (CLEAN, `refs: 2`). A symlinked `.git/objects` → `scan-failed`. The output is still rows only, and the files are the operator's own, so this is containment hygiene, not a leak.

**Fix:** `lstat` `objects`, `refs`, `packed-refs` and `HEAD`, and refuse a symlink (`repo-not-contained`), or state it in §16.3 alongside the alternates.

## Residuals for design §16.3

Each must be written into §16.3, or closed by a fix:

7. A gitleaks crash with core dumps enabled (`ulimit -c` raised; off by default on macOS) could write its memory to `/cores`. Set `GOTRACEBACK=none` in gitleaks' environment.
8. Until fixed: a type change (SS-01), PATH folders inside the repository (SS-05), case-colliding ref names (SS-09).

### New findings

**[RC-01] "Inside the repository" is decided by spelling, not identity** · LOW · `findOnPath`/`versions` (`inside(realOr(d), root)`), `scan-secrets.mjs` · contradicts §5.5 "passing over any folder inside the repository" and §16.2 item 12
- **Problem:** on macOS's case-insensitive volume, the repository given as `…/Client/repo` while direnv put `…/client/repo/bin` on PATH, or the reverse, or a PATH folder spelled through `/System/Volumes/Data`, isn't recognised. The repository's own `git --version`, `gitleaks version` and `gitleaks git --help` run.
- **PoC:** `RC-01a`, `RC-01b`; lab `r-path.sh` cases b, c and d.
- **Fix (validated in a lab script):** decide by identity, not by string. Walk the real path of each PATH folder, and of each found program, up through its parents, comparing `statSync(…).dev:ino` with the repository root's and its git folder's. That catches case, Unicode normalisation, firmlinks and bind mounts. `realpathSync.native` fixes case but not firmlinks.

**[RC-02] `not_scanned` labels are `.git/modules` folder names, shown unchecked** · LOW · `submoduleDirs`, `scanSecretsText` · a regression from the SS-03f fix
- **Problem:** row paths are held to the strict pattern, but these labels aren't. A folder name with ESC sequences and a newline reached text mode raw: it can clear the screen and forge a second `CLEAN:` line plus an "IGNORE PREVIOUS INSTRUCTIONS…" line. In JSON it's escaped, but it still carries injected text to the calling skill. `.git/modules` isn't history, but a repository handed over as a folder or archive carries it.
- **PoC:** `RC-02`.
- **Fix:** hold each label to the row path rule (no `\p{C}` or `\p{Z}` other than a space, at most 1,024 characters). Replace a label that fails with a count ("1 submodule folder with an unprintable name"), and in text mode never print a field unescaped. Part 2 should treat `not_scanned` like scan rows for injection.

**[RC-03] `doctor` and `version --json` have no repository to pass over** · INFO · `doctor.mjs` (`findOnPath(…, env)` with no `skip`)
- **Problem:** run from inside a repository whose `bin/` direnv put on PATH, `version --json` runs that folder's `gitleaks version` and `git --version` and reports `scan-secrets: ready`. `scan-secrets` itself passes them over.
- **PoC:** `RC-03`.
- **Fix:** pass over PATH folders inside the current folder's git repository (find `.git` upward from `process.cwd()`), or state it in §16.3 and §16.2 item 12 ("doctor and version can't know the repository").
