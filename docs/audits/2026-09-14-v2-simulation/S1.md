## F-S1-001 — Updater uses tracked consent rather than local SQLite consent

**Severity:** MEDIUM. **Category:** quality/config. **Effort:** S–M. **Status:** open; no product fix attempted.

**Locations:** `scripts/update-opchain.mjs:160–165`, `scripts/update-opchain.mjs:569–575`, and identical generated copies including `plugins/opchain/skills/oc-update/scripts/update.mjs:160–165`. Compare `scripts/telemetry.mjs:120–138`, which reads `telemetry_meta.consent_enabled`, and `skills/oc-checkpoint-protocol/SKILL.md:749–757`, which makes tracked telemetry metadata historical rather than authorizing. `skills/oc-update/SKILL.md:85–89` requires unchanged telemetry state reporting and exit 2 for enabled unhealthy telemetry.

`telemetryHealth` reads `.checkpoints/oc-telemetry-ops.checkpoint.json` and returns healthy/OFF immediately unless its historical handle says enabled. It never reads local consent. Consequently a real locally enabled 2.0 store is classified OFF if the tracked checkpoint is absent, and an unhealthy enabled store gets updater exit 0. Conversely, stale/copied tracked metadata can falsely report ON or trigger exit 2 on a machine that has never opted in. The telemetry command and update command disagree about the same unchanged bytes.

| Synthetic state | Expected updater check | Actual updater check | Actual telemetry status |
|---|---|---|---|
| SQLite enabled, healthy; no tracked telemetry checkpoint | Exit 0, ON | Exit 0, OFF | Exit 0, ENABLED, one run |
| SQLite enabled, `runs` table absent; no tracked telemetry checkpoint | Exit 2, ON/unhealthy | **Exit 0, OFF** | Exit 1, `no such table: runs` |
| SQLite disabled; stale tracked enabled flag | Exit 0, OFF | Exit 0, ON | Exit 0, OFF |
| Tracked enabled flag copied; no local SQLite | Exit 0, OFF | **Exit 2, ON/database missing** | Exit 0, OFF |

Evidence pairs are `variant-*.json` and `telemetry-*.json`. In every case the complete consumer byte inventory remained unchanged. The main mixed-host scenario repeats the healthy-enabled mismatch, accounting for the fifth failing assertion. This does not enable recording, alter consent, or lose history. It does violate the release's promised update-health signal and misdirects users into repairing intentionally absent state.

The previous targeted updater audit (`docs/audits/2026-09-12-oc-update.md`) claims preservation and enabled-unhealthy handling, but does not record this cross-contract disagreement. Existing updater tests seed legacy tracked consent; newer telemetry tests correctly require machine-local consent. Both sets pass independently, leaving their integration mismatch undetected.
