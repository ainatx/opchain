# v2.0.1–v2.0.3 feature-execution audit

**Date:** 2026-09-21 · **Auditor:** oc-release-ops (installed copy 2.0.2) · **Subject:** catalog 2.0.3 (`da202a0`, deployed as `8bad1a0`)
**Question:** when the skills are called, do the features promised in 2.0.1, 2.0.2 and 2.0.3 actually run?

## Verdict

The shipped code works. Wherever it runs, each feature does what the changelog says, and distribution is clean: the site, zip, public mirror, MCP registry and tags all say 2.0.3.

Three problems remain:

1. **On this machine, calling the skills runs none of the 2.0.1 behaviour.** The opchain plugin isn't loaded for this repository. The only installed copy is 1.9.0, and it's scoped to a single dose-app worktree. The global skills are 2.0.2.
2. **Two promises are broader than the code.** "Every task now begins and ends" is false in any repository without `.checkpoints/`. "check-release-surfaces.mjs now gates this" covers only three of the six surfaces the changelog names.
3. **The release pipeline's own close-out step didn't run for 2.0.3.** The oc-release-ops checkpoint still describes 2.0.2 as in-flight, and the 2.0.x SessionStart hook now shows that stale next action at every session start.

## Findings

### 1. HIGH: the 2.0.x plugin features aren't executed when you call skills on this machine

| Surface | Installed | Current |
|---|---|---|
| `~/.claude/skills/oc-*` (36) | 2.0.2 | 2.0.3 |
| opchain plugin | 1.9.0, project scope, only `dose-app/.claude/worktrees/opchain-skill-upgrade-934ee8` | 2.0.3 |
| Marketplace clone `~/.claude/plugins/marketplaces/opchain` | 1.9.0 (`70ae8d3`, last updated 2026-09-03) | 2.0.3 (`2ee174b`) |
| `enabledPlugins` (user settings) | `{}` | — |

So in this repository (and anywhere except that one worktree), no `Task started:`, no `Task ended:`, no checkpoint context and no next-skill pointer. None of 2.0.1's user-visible change reaches you. Content drift between the global 2.0.2 skills and 2.0.3 is small: the frontmatter version, plus two oc-release-ops references that still describe hero-ver as "review only" when it's now gated. `oc-update` is repo-local by design, so nothing ever tells a `~/.claude/skills` user they're behind.

When the plugin *is* loaded next to the global copies, both register (`oc-orchestrator` 2.0.2 and `opchain:oc-orchestrator` 2.0.3, seen in SIM-1's init). Which version runs depends on how the skill is named.

**Fix (you, interactive):** `/plugin marketplace update opchain`, then install or enable `opchain@opchain` at user scope. Then either remove the `~/.claude/skills/oc-*` copies or accept two versions side by side.

### 2. MEDIUM: "Every task now begins and ends" is false outside checkpoint repos

`task-end.cjs` exits silently when `<root>/.checkpoints` is missing (line 19) or stdin isn't JSON. `session-state.cjs` prints the start stamp before either check. So every new consumer repository, every repository before its first checkpoint, and every non-git directory gets a start with no end (SIM-2, SIM-4). `tests/task-end-hook.test.js` only covers the with-`.checkpoints` case, and no test asserts `Task started:` at all.

**Fix:** drop the `.checkpoints` guard and the malformed-stdin exit from `task-end.cjs` (the stamp doesn't need a repository), and add no-checkpoint cases for both hooks.

### 3. MEDIUM: the stamps mark sessions and turns, not tasks

Stop fires after every assistant reply. SessionStart fires on `startup`, `resume`, `clear` and `compact`. So a multi-turn task prints `Task ended:` after every reply, and a resumed or auto-compacted task prints a fresh `Task started:` partway through (SIM-3, SIM-4). The changelog's "first SessionStart hook" means first in the hook array, not the first start of the task.

**Fix:** either label by event (`Session resumed:` / `Context compacted:` on non-startup sources, `Turn ended:` on Stop), or narrow the changelog and site wording to "session start / each turn's end".

### 4. MEDIUM: the 2.0.3 surface gate covers three of the six surfaces the changelog names

Of hero, README, mirror README, plugin README, skill-library callout and skill-page chip, `check-release-surfaces.mjs` probes the hero, the README and the callout. A stale mirror README, plugin README or skill-page chip passes CI (SIM-6 M4–M6). A lagging styleguide patch badge also passes (M7) because it's probed only at minor level, even though `site-release-surfaces.md`'s Patch column requires the full patch version. All of these surfaces are correct today; nothing enforces it.

**Fix:** add full-semver probes for `mirror/README.md` (`Opchain x.y.z ·`), `plugins/opchain/README.md` (`> **Opchain x.y.z.**`) and the styleguide badge, plus a minor-level probe for `skills/[id].astro`'s `inloop-tag`. Or reword the 2.0.3 entry to name the three surfaces actually gated.

### 5. LOW: the `skills.coverage` fix is only in one place

The generated description now says reserved and unwired, which matches the code (no read site gates on it). These still say otherwise:
- `src/lib/flags/registry.js:19`: "Show / hide a oc-stack-forge pack"
- `site/src/pages/architecture.astro:532`: "drives `skills.coverage.<id>.enabled` · consumed by oc-stack-forge · oc-app-architect · …" (public page)
- `.claude/commands/flag.md:35`: "Per-pack oc-stack-forge coverage option", with no "reserved"
- The CLAUDE.md "Feature flags" namespace list omits `skills.coverage.*`.

The 30 flags are also in the public browser snapshot, though nothing reads them.

### 6. MEDIUM: oc-release-ops never closed out 2.0.3 (Phase 5 step 6 skipped)

`.checkpoints/oc-release-ops.checkpoint.json` still has `current_release.semver: "2.0.2"`, step `pr-556-awaiting-ci` and status `in_progress`. All three `next_actions` (extend the L4 hero, the honesty-copy PR, gate hero-ver) already shipped in #553 and #556. `oc-code-auditor`'s first next action is the same completed work. With the plugin loaded, the SessionStart hook shows that stale pointer (`next: oc-release-ops: Site closeout PR: extend changelog open-hero L4 …`) at the start of every session in this repository (seen in SIM-1).

**Fix:** write the 2.0.3 shipped state (`current_release` 2.0.3, `tag`, `production`, `monitoring`, `prior_release` 2.0.2, phase `shipped`, status `complete`) and clear the finished next actions in both checkpoints.

The baseline was refreshed to `8bad1a0` in #559, but the scheduled Canary (`47 13 */4 * *`) and Deploy lag (`17 14 */4 * *`) jobs last ran on 2026-09-17, before the refresh, and both failed. #554 is still open. The next scheduled runs are today (2026-09-21) at about 13:47 and 14:17 UTC. Expect Deploy lag to flag again, correctly this time: #547 and #549 changed `plugins/`, `skills/`, `site/` and `package-lock.json` after the approved runtime and haven't been deployed. The changelog text also names `f196207` as the approved runtime, which #559 superseded.
