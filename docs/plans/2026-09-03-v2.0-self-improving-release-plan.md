**Why this release is a major.** The spec's "honest BREAKING case" stands:
wire 1.2 changes the *read* contract of `eval_scores[]` (in-file array becomes
a bounded window; the archive of record moves to
`.checkpoints/history/<skill>.eval.ndjson`) and the *merge* contract on that
path (union by `run_id || at`). Old files keep validating; what moves is a
documented contract two skills (`oc-orchestrator`, `oc-cost-ops`) depend on.
`skills/CHANGELOG.md` policy calls that BREAKING; `semver-decisions.md` item 1
must be widened in the same release or a literal reading files 1.2 as Minor
(spec Appendix A.10).

**Why now.** v1.9 shipped the assurance rail: the pipeline can now *prove* what
it did (qa manifests, hardening replays, evidence bundles, eval history in
checkpoints). 2.0 is the first release that *uses* that evidence — every
Evaluator verdict, every FAIL report, every postmortem becomes a source the
pipeline reads back, under human gates. The two v1.9 skills that produce the
richest evidence (`oc-qa-ops` budgets, `oc-security-hardening` replays) are
exactly the emitters Sprint 3 harvests first.

**The two sequencing constraints (both inherited from v1.9, both mechanical):**

1. **The deploy-freeze window.** `scripts/check-release-tag.mjs` compares the
   working catalog to the tagged one *by skill identity*. The moment
   `skills/oc-hindsight/` and `skills/oc-evolve/` exist on `main`, the guard
   returns `tag-version-mismatch` with `countDrift: true` ("this tree is the
   NEXT release still wearing the 1.9.0 number") and production deploys are
   refused until `v2.0.0` is tagged. Answer, narrower than v1.9's
   blanket rule: **no new `skills/<id>/` directory, no `version:` bump, and no
   text naming `oc-hindsight`, `oc-evolve` or wire 1.2 merges to `main`
   outside the Sprint 6 product-half PR**, which carries the two new
   directories *and* the full 35× lockstep bump in one merge. The only frozen
   interval is merge → tag, one sitting. Reciprocal edits naming none of those
   three things — the oc-orchestrator `memory_user_edits` fix and v1.9
   routing-row backfill, `semver-decisions.md` item 1, the
   `version-locations.md` rework, the `site-release-surfaces.md` F7 path fix —
   merge as ordinary substrate PRs, which keeps the long-lived skills branch
   small enough to rebase for three to four weeks. #482 is the precedent: a
   `skills/`-touching docs PR merged to `main` between the tag and this plan
   without tripping the guard, because it moved no skill identity.
2. **The mirror trap (new weight this release).** Every `main` push touching
   `skills/`, `plugins/`, `.claude-plugin/`, `mirror/` or `LICENSE`
   re-snapshots the public repo — the plugin paths matter as much as `skills/`
   here, and the first draft of this plan got that wrong. The wire-1.2 section of
   `oc-checkpoint-protocol/SKILL.md` propagates into all 35
   `references/checkpoint-protocol.md` bundles (`sync-bundles`), so a
   BREAKING protocol doc on `main` at catalog `1.9.0` would publish a
   contradiction (the protocol says 1.2, the catalog says 1.9). Same answer:
   the protocol text rides the product-half PR. Repo-side code *outside*
   `skills/`, `plugins/` and `.claude-plugin/` — the validator accepting 1.2,
   the merge drivers, the four engines, the repo-local hooks, the tests — is
   not mirrored and merges freely throughout; see §2 D-A for the
   accept-but-don't-stamp rule that makes this safe. **Everything under
   `plugins/opchain/` and `.claude-plugin/` is mirrored, so it rides the
   skills branch** (D-E), not the substrate branch: a mid-release snapshot
   publishing 2.0 hooks and kits for skills the public catalog does not have
   is the same protocol-ahead-of-catalog contradiction this section exists to
   prevent. **Post-flip this constraint dissolves** — `mirror-public.yml` is
   disabled at C5 and deleted at C8 — and is replaced by the submodule-pin
   relationship (D-H item 2). Since D-H puts the flip *before* Sprint 1, the
   mirror trap is in practice a constraint on nothing in this plan; it is kept
   documented because it governs any 2.0 work that starts before C7 goes
   green, which is exactly what Sprint 0 forbids.

### 2.2 Decisions the spec left open (new here)

**D-A — Accept-but-don't-stamp.** `scripts/checkpoint.mjs` gains `"1.2"` in
`ACCEPTED_SCHEMA_VERSIONS` in Sprint 1 and merges to `main` freely; the
`SCHEMA_VERSION` flip to `"1.2"`, the 16-file stamp sweep of opchain's own
checkpoints, `.checkpoints/README.md`, and the protocol SKILL.md section all
ride the Sprint 6 product-half PR. Between Sprint 1 and the cut, `main`
validates 1.2 files but writes 1.1, and **`rotate` refuses any checkpoint
stamped below 1.2** (`rotate-requires-1.2`) — without that refusal, rotation
would truncate a live `eval_scores[]` while the file still says `"1.1"`, which
is exactly the read-contract break the major exists to announce. Pre-cut, only
the 1.2-stamped fixtures rotate; the Sprint 6 stamp sweep unlocks it for real
checkpoints. Two stamping sites, not one: `scripts/telemetry.mjs:46` hard-codes
its own `SCHEMA_VERSION = "1.1"` and forces `protocol_version` on every write of
`oc-telemetry-ops.checkpoint.json`, so Sprint 1 makes it import
`SCHEMA_VERSION`/`ACCEPTED_SCHEMA_VERSIONS` from `checkpoint.mjs` (one source,
pinned by a test that no second `SCHEMA_VERSION` literal exists under
`scripts/`). Otherwise the next `npm run telemetry` after the cut silently
re-stamps that checkpoint back to 1.1 and the sweep cannot stay green.

**D-B — Kit distribution (the question the spec's "repo-local kit" phrase
leaves unanswered: how does a *consumer* repo get `scorecard.mjs`,
`hindsight.mjs`, `evolve.mjs` and the hooks?).** Skills are global and
identical everywhere; the engines are repo-local by design. Plan of record: the kit ships inside the plugin under
`plugins/opchain/kits/` (canonical source stays `scripts/` in this repo;
`scripts/sync-plugin-kits.mjs` + `npm run sync-plugin-kits:check` join
`pretest` beside `sync-plugin-skills:check` — **a Sprint 3 substrate
deliverable**, since B0 depends on it). The manifest is explicit, because the
engines depend on more than themselves: `scorecard.mjs`, `hindsight.mjs`,
`evolve.mjs`, `prompt-eval.mjs`, **`checkpoint.mjs`** (`rotate`,
`evalTrendDeclining()`), **`merge-checkpoint.mjs`** (the eval_scores union),
`merge-hindsight.mjs`, a kit-local driver installer, and the two hook scripts.
A kit missing `checkpoint.mjs` would give a consumer repo a `scorecard rotate`
that shells out to a file it does not have.
Both new skills gain an additive **`init`** verb (`/oc-hindsight init`,
`/oc-evolve init`) that copies the kit into the consumer repo, appends the
`.gitattributes` rules, registers the merge driver via the existing
`install-git-drivers.mjs` pattern, creates the `.opchain/` store dirs, and
writes `.opchain/self-improvement.yaml` (the Q10 manifest). `init` is
idempotent and prints a diff; it never touches CLAUDE.md except to add the
delimited scorecard block.

**`init` must not arm the commit gate — the predicate gets narrowed
(decided 2026-09-08).** `plugins/opchain/hooks/pre-commit-gate.cjs:171` opts a
repo in when *any* of `OPCHAIN_GATE=1`, `.checkpoints/`, or `.opchain/` exists,
and the gate is fail-closed (rule 0): once armed it denies every `git commit`
run through Claude Code's Bash tool until `.checkpoints/oc-bug-check.checkpoint.json`
records a `PASS` bound to the current tree hash. So `init` creating `.opchain/`
would silently make a stranger's next commit fail in a repo they never opted in.

Two things ruled out the softer fix. `OPCHAIN_GATE=0` **does not disable the
gate** — the predicate tests `=== "1"` as an enabler, never `"0"` as a
disabler, so with `.opchain/` present that variable is inert; an earlier draft
of this plan told users to set it, which would have handed them a fix that does
nothing. And the only real escapes are per-commit (`--no-verify`,
`OPCHAIN_BYPASS=1`) or deleting the directory.

So Sprint 3 narrows the predicate instead: a repo whose **only** `.opchain/`
content is self-improvement state (`self-improvement.yaml`, `hindsight/`,
`rules/`) is not gated; any repo carrying a gate-relevant manifest
(`qa.yaml`, `hardening.yaml`, `compliance.yaml`, `pm.yaml`, `data-contracts/`)
stays gated exactly as it is today, so no existing user is de-hardened. `init`
still prints what it created and what it did *not* turn on. Tests: a temp repo
with only self-improvement state commits freely; the same repo plus `qa.yaml`
is gated; a repo with `.checkpoints/` is gated regardless. This is the one
place 2.0 edits a shipped v1.9 mechanism, and it is a deliberate un-surprising
of a fail-closed gate, recorded here rather than discovered by a user.

**Zip installs:** `scripts/make-skills-zip.sh` packages `skills/` only, so a
zip user has the two SKILL.md contracts but no engines. `init` detects that
(no `kits/` beside the skill) and refuses with a pointer to the plugin
install rather than half-configuring a repo.

**Alternative considered:** ship engines opchain-only in 2.0 and defer
consumer install to 2.1 — rejected because a 2.0 whose headline skills only
work inside one repo is not a 2.0. **This is the decision most worth the
user's eye at the gate.**

**D-C — Hook placement.** Repo-local (this repo, installed by `init` in
consumer repos): `.claude/hooks/outcome-scorecard.sh` (Stop → harvest;
SessionStart → inject) and `.claude/hooks/hindsight-retrieve.sh`
(UserPromptSubmit + SessionStart). Plugin: `session-state.cjs` gains a
read-only "active directives + top-k lessons" block when the stores exist
(the surface users already read at session start), and `hooks.json` gains a
UserPromptSubmit entry for a fast-exit `hindsight-retrieve.cjs`. **The plugin
Stop hook does not harvest** — `next-suggestion.cjs` has a 5-second timeout
and a "print nothing when nothing to say" contract; harvest belongs to the
repo-local Stop hook that `init` installs. Add both new skills to
`.claude/hooks/checkpoint-hygiene.sh`'s `ENFORCED_SKILLS` (they write
checkpoints).

**Single-owner rule.** In any repo running both the plugin and `init`-installed
hooks — this one, per the Sprint 5 dogfood — three SessionStart injectors and
two UserPromptSubmit injectors would otherwise fire per event, doubling the
≤ 12-line and top-k ≤ 3 bounds. So: the plugin's `session-state.cjs` and
`hindsight-retrieve.cjs` fast-exit when `.opchain/self-improvement.yaml` sets
`hooks.owner: repo` (which `init` writes) or when the repo-local hook for the
same event is registered in `.claude/settings.json`. Every injector, plugin
included, honours `OPCHAIN_HINDSIGHT_OFF` / `OPCHAIN_EVOLVE_OFF` and the
manifest keys. `hindsight-retrieve.cjs` calls
`${CLAUDE_PLUGIN_ROOT}/kits/hindsight.mjs query` rather than re-implementing
BM25 — the plugin ships without `scripts/`, and retrieval implemented twice
drifts by definition.

**Hook contract (all four new hooks).** Exit 0 always; empty stdout on any
error; never emit `decision` or `permissionDecision`; honour `stop_hook_active`;
explicit timeouts in both `settings.json` and `hooks.json` (Stop 10,
SessionStart 5, UserPromptSubmit 2). This has to be stated because the repo
carries two opposite conventions — `next-suggestion.cjs` never emits a decision,
while `pre-commit-gate.cjs` rule 0 fails closed — and a new Stop hook that
inherited rule 0 would block every session end, while a UserPromptSubmit hook
exiting 2 would erase the user's prompt. Appendix E pins one case per hook:
engine throws → exit 0, empty stdout.

**D-D — Durable audit reports live under `docs/audits/`** in this repo (the
dir already exists with the 2026-08-22 OSS audit); the code-auditor contract
names the location as repo-policy-overridable with `audits/` as the default
for repos without a `docs/` tree.

**D-E — Branch topology.** Two long-lived branches, mirroring v1.9's pattern:
`claude/v2-0-substrate` (Sprints 1–2 repo-side code, merged to `main` per
sprint as normal PRs — nothing under `skills/`) and `claude/v2-0-skills`
(all `skills/` content from Sprints 1–5, merged **only** as the Sprint 6
product-half PR). Engine code for Sprints 3–5 (`hindsight.mjs`, `evolve.mjs`,
hooks, tests, flags registry entries, plugin kits) also merges per sprint via
the substrate branch — a flag registry entry for a skill that does not yet
exist on `main` is refused by `check-skill-flags` in strict mode, so the two
`skills.registry.*` and two `skills.command.*` entries are the one code edit
that rides the product-half PR (same as v1.9).

**D-H — 2.0 ships from the product repo; the OSS split goes first
(decided 2026-09-08).** Phase C of the split is stopped at C1 (manifest
prepared, `flip now` pending). Rather than cut a major catalog release
monorepo-side and then immediately re-do the whole release surface in a
two-repo layout, the split completes first and **2.0 becomes the first
product-repo release** — handoff Phase D. Consequences, in the order they bite:

1. **Sprint 0 gains a hard precondition:** Phase C2 (extraction) through C7
   (cut-over verification) complete and green. C1's path freeze covers every
   entry in `split/product-paths.txt` — `skills/`, `plugins/`,
   `.claude-plugin/` and ~25 scripts — so no 2.0 sprint can merge while it
   holds. Sprints 1–5 start after C6's consume PR merges, not alongside it.
2. **The mirror trap dissolves, and is replaced.** `mirror-public.yml` is

**The recorded-fixture trap, and the split that avoids it.** A committed
answer fixture cannot change when a rule is adopted, so scoring `regress`
against one would compare the fixture with itself: every gate green,
`eval_delta` permanently 0, Q9 (c) and (d) passing without proving anything.

against the committed fixture — that proves the *grader*, not the gate. (b) **At
adopt time** the routing answers must be freshly produced by the skill after the
rule is applied: `evolve.mjs adopt` refuses a result file whose `run_id` or run
timestamp predates the rule's `proposed_at`, or whose recorded hash of the
routing surfaces (skill `description:` frontmatter + the orchestrator routing
table) differs from HEAD.

`graded_by: oc-prompt-ops` and the baseline sha; `evolve.mjs adopt` refuses a

own gate input, and evolve would be writing into `prompts/opchain-eval/` across

`adopt` refusing outright". Flag convention (also new — neither prompt-ops nor git-ops documents

## 3. Per-deliverable specs (summary — the SKILL.md files and Appendix C/D are normative)

### 3.1 Wire 1.2 (`oc-checkpoint-protocol` + `scripts/checkpoint.mjs` + `scripts/merge-checkpoint.mjs`)

- **Schema** (Appendix C has the full draft section): `eval_scores[]` entries
  gain optional `run_id` (string), `verdict` (`PASS|FAIL|WARN`), `evidence_ref`
  (repo-relative path). **1.2-stamped writes MUST carry `run_id` or `at`**
  (the dedupe key); the validator errors on a 1.2 file whose entry has neither,
  and merely warns on 1.0/1.1 files.
- **Rotation:** the in-file array is a bounded recent window (default 20
  entries per skill; `checkpoint.mjs rotate <skill>` spills older rows,
  newest-last, to `.checkpoints/history/<skill>.eval.ndjson`). The existing
  32 KB warn threshold is the *only* size number — rotation is what the warning
  now recommends. Rows are one JSON object per line, identical shape to the
  in-file entry plus `skill`, always terminated with `\n`. The ndjson carries a
  5,000-row cap, after which `rotate` archives to
  `history/<skill>.eval.<year>.ndjson`; the cap and the year archive are Sprint 1
  deliverables with tests and a Directory Convention row, not the risk-register
  footnote they started as.
- **Merge:** `merge-checkpoint.mjs` gains a union case on the `eval_scores`
  path — union by `run_id || at`, structural-equality fallback for legacy
  entries. **File order is explicitly not meaningful:** `merge=union` is
  line-based and, per git's own attribute docs, leaves added lines in arbitrary
  order — it can also duplicate a row two branches appended at different offsets
  and splice two rows together when a file lacks a trailing newline. So every
  reader (scorecard, evolve, orchestrator) sorts by `at` and dedupes by the row
  key after reading, rotation never relies on positional order to pick what to
  archive, and the CI check is a `history-integrity` pass — every line parses as
  JSON, carries `skill` and (`run_id` or `at`), and no key repeats — not merely
  a scan for conflict markers, which would catch neither a corrupt nor a
  duplicated line. This is net-new logic: today every
  divergent array is atomic (`deepEqual` → conflict), and the only path-set
  concept, `TELEMETRY_PATHS`, is newer-side-wins — the semantic opposite of
  union. Add a `UNION_PATHS` set beside it. `.gitattributes` gains
  `.checkpoints/history/*.eval*.ndjson merge=union` — the `*.eval*` glob, not
  `*.eval.ndjson`, so the year archives (`<skill>.eval.2026.ndjson`) are covered
  too. **Known limit:** GitHub's
  server-side merge runs neither custom drivers nor the `union` attribute; a PR
  whose ndjson append collides with `main` shows a conflict that a local
  `git merge` resolves trivially. CI adds a no-conflict-markers check over
  `.checkpoints/history/`.
- **Doctrine:** the sentence "A wire bump is *never* a breaking change here"
  is rewritten in the same section: a wire bump is *additive on disk* and may
  still be BREAKING when it moves a documented read or merge contract — 1.2 is
  the first such case. `semver-decisions.md` item 1 widens accordingly.
- **Directory Convention** — the tree today lists neither `history/` (prose
  mentions only, at :340/:354/:435) nor `usage.sqlite` nor `scorecard.json`.
  Three additions: `history/<skill>.eval.ndjson` (tracked, append-only,
  archive of record) beside the existing `history/<skill>.<date>.checkpoint.json`
  reset archives, `scorecard.json` (tracked, derived), and the gitignored
  `usage.sqlite` made explicit.
- **One writer, one row identity.** `checkpoint.mjs rotate` owns
  `history/<skill>.eval.ndjson`. The scorecard's report-file scan writes to a
  separate `history/<skill>.reports.ndjson` and derives a deterministic
  `run_id` (`<report-path>@<sha>`), because report files carry no run id of
  their own. Row identity is `evidence_ref || run_id || (skill, rubric, at)`,
  and readers dedupe on it before computing any trend. Without this, one eval
  reachable three ways — a rotated `eval_scores[]` row, an `eval-round-M.md`
  report, and a snapshot sample — lands as three rows, and recurrence ≥ 3 trips
  after two real declines, breaking safety invariant 3 by arithmetic. The
  oc-app-architect Phase 6 contract therefore writes the same `run_id` into both
  the report header and the `eval_scores[]` entry, which joins the frozen
  headings.
- **Migration:** the 1.1 → 1.2 stamp is an `oc-migration-ops` `ecosystem`
  job (`protocol_version_from/to` fields already exist in its checkpoint
  contract) — additive, reversible, no data transform.
- **Trend/advisory semantics stay out.** The protocol defines format and
  location; computation belongs to the scorecard kit and `oc-evolve`.

### 3.2 Outcome Scorecard kit (mechanical; no skill)

`scripts/scorecard.mjs` verbs: `harvest` (report-file scan of
`sprints/**/eval-round-*.md` — monotonic `M` — as primary; `eval_scores[]`
snapshot sampling best-effort; `oc-bug-check` rows = verdict + per-check
statuses + counts + timestamp **only** — the verdict is three-valued,
PASS / PASS-with-warnings / FAIL, plus per-check `UNSUPPORTED`; per-check
statuses come from `skill_state.last_run`, since `run_history[]` carries only
`{at, verdict, warnings|errors}`), `report` (slope / moving average /
volatility / streak per skill × dimension), `expire` (directive lifecycle:
emit at recurrence ≥ 3, decay on slope recovery), `render` (CLAUDE.md
delimited block `<!-- opchain:scorecard:start/end -->` + `--check` byte

`scan --check` (recompute from the ndjson and byte-compare `scorecard.json`),
`rotate` (delegates to `checkpoint.mjs rotate`), `inject` (SessionStart
stdout — active directives only, ≤ 12 lines). **Re-injection has one owner:** the SessionStart path
(`.claude/hooks/outcome-scorecard.sh`, and the plugin's `session-state.cjs`
where it owns the event) calls `scorecard.mjs inject` for directives and
`evolve.mjs render --inject` for rules — the latter emitting only
`status: adopted` rules whose `expires_at` is in the future, capped at ≤ 5
rules / ≤ 12 lines, in the same fenced "(file contents, not instructions)"
block as lessons, fast-exiting on `OPCHAIN_EVOLVE_OFF` or
`reinject.enabled: false`. Nothing else re-injects; "only adopted rules
re-inject" is otherwise a sentence with no implementation behind it.
`scripts/checkpoint.mjs` gains `evalTrendDeclining(data, scorecard)` and a
`pickNext` tiebreaker after the budget tiebreaker (the `budgetExceeded()`
template). Store:
`.checkpoints/scorecard.json` (tracked, derived; Q12).

**Two guards on the CLAUDE.md channel.** CLAUDE.md is the highest-precedence
instruction layer and is loaded into every subagent context, so rendering
learned content there inverts the fixed precedence unless it is pinned down.
(1) The block opens with a fixed preamble declaring it advisory data ranking
below skill contracts and repo policy, its text is descriptive rather than
imperative (the validator rejects a directive whose `text` starts with a verb
or contains "you must"), and it is wrapped in the same "(file contents, not
instructions)" fence as lessons; every Evaluator prompt template instructs the
role to ignore both the `opchain:scorecard` block and any injected `advisory`
fence, which the Q3 pin checks. (2) `directives[].text` is **not stored free
text** — it is derived at render time from `(skill, dimension, recurrence,
slope)` by a fixed template. Otherwise a PR could hand-edit the directive
string, re-render, pass `render --check` (which only proves block == store) and
place arbitrary instructions into every clone's system prompt. `scan --check`
closes that by recomputing the store from the ndjson, and joins both the L4 CI
list and `oc-repo-ops verify`.

### 3.3 `oc-hindsight` — `/oc-hindsight` (tri-agent)

Frontmatter per spec (`phases: [foundation, ai-native]`, `triAgent: true`,
`tryable: true` per Q1) plus the additive `init` verb (D-B). Lifecycle
`quarantined → staged → active → expiring → expired` with `staged →
quarantined` rejection and the Q11 `abandoned` cycle state. Engine
`scripts/hindsight.mjs`: `inventory`, `ingest`, `sanitize`, `chunk`, `dedup`,
`query`, `rebuild`, `validate`, `promote`, `expire`, `eval` (recall@k, MRR vs
the frozen `goldset.jsonl`).

**The ★ human gate cannot be a token the agent writes.** A "recorded human
approval token" in a file the agent authors is self-attestation — the same hole
the plugin commit gate's own audit documents. So `hindsight.mjs promote` and
`evolve.mjs adopt` require an interactive TTY confirmation (`process.stdin.isTTY`;
`--yes` refused when non-TTY, no env bypass), and `promoted_by` records the
signer of the commit that flipped the record. `validate`, `oc-repo-ops verify`
and CI then check that every `status: active` lesson and `status: adopted` rule
was introduced in a signed commit carrying an `Approved-by:` trailer. Both
SKILL.md "Honest limits" sections say plainly that the token alone is not the
gate; the commit signature is. Stores under `.opchain/hindsight/`: `lessons.jsonl`
(tracked, source of truth; only `status: active` retrievable),
`quarantine.jsonl` (tracked, never injected), `manifest.json` (sha-gated
incremental reingest), `goldset.jsonl` (tracked), `index.json` (gitignored
BM25, rebuilt on demand). Merge driver `scripts/merge-hindsight.mjs`, **3-way per record** — if one side
equals base, take the other; apply most-restrictive status, max counters and
newest timestamps only when *both* sides diverged from base; a record deleted on
one side and modified on the other is a real conflict. A naive
"most-restrictive-wins" union would silently revert a ★ human promotion
(base `staged`, ours `active`, theirs `staged` → `staged`), undoing a gate
decision without so much as a conflict; the checkpoint driver it is modelled on
is 3-way for exactly this reason. Registered by `install-git-drivers.mjs`. Retrieval hook injects a fenced
`advisory` block with source citations, top-k ≤ 3, fast-exit when no store,
no hint, or kill switch set. **The hook re-checks freshness and status at
inject time:** it compares `index.json`'s recorded sha of `lessons.jsonl`
against the file's current sha and rebuilds (or fast-exits) when stale, then
re-reads `status: active` from `lessons.jsonl` for each hit. Otherwise a lesson
silenced through its lifecycle — retired, expired, `--abandon`ed, or demoted by
a merge — keeps being injected until someone happens to run `rebuild`, making
"only `status: active` is retrievable" true of the file but not of the hook. Emitter contracts it harvests: `oc-code-auditor`
`docs/audits/<date>-<scope>.md`, `oc-monitoring-ops` `:lessons:` marker
blocks, `oc-app-architect` `eval-round-M.md` (frozen headings),
`oc-bug-check` verdict rows. **Secret redaction covers every verbatim copy, not just the bug-check row.**
Hindsight copies `sources[].excerpt` verbatim out of FAIL reports, postmortems
and the committed `docs/audits/` reports — which by contract carry
hardcoded-secret findings — into tracked `lessons.jsonl` and
`quarantine.jsonl`, and rule `evidence[].excerpt` does the same. So
`hindsight.mjs ingest`/`sanitize` and `evolve.mjs propose` run the oc-bug-check
secret patterns over every excerpt and lesson body and redact to
`[REDACTED:<pattern>]` before any write, quarantine included; the code-auditor
report contract redacts finding bodies the same way; and both `validate` verbs
fail CI on a matching fragment in any tracked store. Methodology reference:
`oc-rag-forge`'s new `references/operational-memory.md`.

1. **Deploy-freeze window.** Same mechanism as v1.9, now identity-based
   (`countDrift`). Mitigation: D-E branch topology; the Appendix B pre-merge
   checklist stages everything; the freeze is merge → tag in one sitting.
2. **~~OSS-split timing fork~~ — decided 2026-09-08: the flip goes first.**
   See D-H (§2.2). This is no longer a risk to manage but a sequencing
   commitment, and it is the single largest schedule item in the release. What
   remains a risk is the *dependency*: 2.0 cannot start Sprint 1 until Phase C
   completes, so any slip in C2–C7 is a 2.0 slip, and the path-freeze in C1

   extraction runs. Do not attempt to build sprints under the freeze.

3. **The BREAKING message reaches every installed user at once.** The
   `/install` SessionStart update-check compares `catalogVersion` and will
   nudge every user the moment `skills.json` says 2.0.0. Mitigation, correcting
   the first draft's: editing the hook copy on `/install` reaches **nobody who
   already installed** — the update check is a shell one-liner users paste into
   their own `settings.json`, so its message text is frozen at install time and
   only ever prints "vX is available … Update guide:
   https://opchain.dev/install#update". The channel that reaches the installed
   base is that URL, so the **`/install#update` section itself**
   (`install.astro` ~:340–380) carries the v2.0 BREAKING note and the
   `oc-migration-ops` sweep command, and §6 and B3 list it as a release-coupled
   surface; the hook-copy edit stays as a secondary fix for new installers.
   `skills/CHANGELOG.md` `[2.0.0]` opens
   with the BREAKING block (what moved, what still validates, the
   `oc-migration-ops` sweep command); `mirror/README.md` carries the same
   three lines. Nothing migrates destructively — the note must say so first.
4. **Prompt injection through learned content.** Load-bearing control: the
   isolated Retrieval Evaluator + human promotion of *every* lesson (Q4) +
   the retrieve hook's fenced `advisory` block + the kill switch (Q10). Regex
   sanitization is defense-in-depth. Sprint 3 ships an adversarial fixture
   (an instruction-shaped "lesson") and pins that it is quarantined and never
   retrievable.
5. **Secret re-commit via the harvest side channel.** `oc-bug-check` FAIL
   reports can embed detected fragments. Harvest rows are verdict + statuses
   + counts + timestamp only; Sprint 2 pins it with a `sk_live_` fixture.
   Also: `docs/audits/` reports are committed and *public* post-split — the
   code-auditor contract warns, and the location is repo-policy-overridable.
6. **Merge drivers are local-only.** `npm prepare` registers them; GitHub's
   merge does not run them and ignores `merge=union`. Accepted: one harvest
   per session per repo makes collisions rare; the CI conflict-marker check
   catches the residue; the protocol section documents the limit.
7. **Hook latency.** Stop-hook harvest must stay under the plugin's 5-second
   Stop timeout expectations even though it lives in the repo-local hook
   (10-second budget in `settings.json`): harvest is incremental (sha-gated
   manifest), and UserPromptSubmit retrieval must be < 300 ms (BM25 over
   ≤ 1k lessons, index cached). Sprint 3 measures both with a timing test.
8. **Evaluator isolation is a convention the Agent tool cannot enforce.**
   Both roles run in the same repo; the pin is structural (Q3 test) plus
   filesystem-only handoff. Residual risk accepted and named in both
   SKILL.md "Honest limits" sections.
9. **Cost of two tri-agent loops.** Ceilings in `budget-gates.md`; cost-ops
   attributes per phase; each workflow owns deferral. The Sprint 5 dogfood
   run records the real cost of one harvest and one reflect → adopt cycle in
   the release notes.
10. **Second maintainer arrives mid-release.** Same table as the v1.9 plan
    §7.5 applies verbatim — nothing in-flight changes content; the R7 audit
    becomes mandatory instead of voluntary; both cut PRs need one review.
11. **Goldset thinness (Q9).** Only routing cases exist today, so a rule
    targeting a real skill hits `goldset-too-thin`. That is the intended
    forcing function — the refusal names the cases to write, and Sprint 4's

12. **`history/` growth.** Tracked ndjson grows forever by design. Rotation

A wire bump only ever adds optional fields on disk. It can still be a BREAKING

on — 1.2 is the first such case, which is why it ships in a major.

### Directory Convention additions

.checkpoints/scorecard.json                     tracked · derived (regenerate with `scorecard scan`)
.checkpoints/usage.sqlite                       gitignored · oc-telemetry-ops metering

### `blockers[].advisory` (optional, 1.2)
A boolean. `true` marks a blocker that must not outrank real execution
blockers — `rankCheckpoint()` demotes it below ranks 1–4. oc-evolve files
pending rule proposals this way, so a proposed rule never sits at the rank-1
`needs: user_decision` position a genuine bottleneck occupies.

### Migration
The `"1.1"` → `"1.2"` stamp sweep is an `oc-migration-ops` `ecosystem` job —
additive, reversible, no data transform. Consumers on 1.1 lose nothing; the
2.0 skills degrade to report-file sources when `history/` is absent.
