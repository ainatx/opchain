## 0. Context and drivers

**Why now, and why fast:** a second maintainer is about to come on board. Two
consequences shape this release:

1. **R10 (release-surface governance) activates on the second-maintainer PR.**
   Until then the sole maintainer decides at discretion and `RELEASING.md` is a
   personal checklist. v1.9 is therefore the *last cut under the simple regime*
   and the *dress rehearsal* for the governed one — run the cut per RELEASING.md
   §6 (the R7 audit prompt) even though nothing yet forces it.
2. **The catalog the new maintainer inherits should already contain the
   assurance rail.** v1.9's whole theme is making delivery evidence reviewable
   and enforceable — exactly the tooling a two-maintainer workflow needs on day
   one.

**Precondition (Sprint 0):** v1.8.3 is still mid-ship. Staging serves main HEAD
(`9f135e5`), prod serves `57ef163`, and no `v1.8.3` tag exists. The v1.8.3
human gate (eyeball staging → `/oc-git-release 1.8.3` → `npm run deploy`) must
complete before any v1.9 work merges to `main`. Nothing in this plan touches
that release.

**The deploy-freeze window (sequencing constraint discovered while planning):**
`scripts/check-release-tag.mjs` fails `tag-version-mismatch` when the tagged
tree's skill count differs from the working catalog's. The four new skills
enter at catalog version `1.8.3` (to avoid a `catalog-split` refusal), so the
moment they merge to `main`, the working catalog has 33 skills against a
29-skill `v1.8.3` tag — **production deploys are refused from that merge until
`v1.9.0` is tagged.** This is the guard working as designed ("the catalog moved
somewhere no tag follows"), but the sequencing answer is stronger than "merge
close to the cut": the four skills must never land on `main` wearing `1.8.3`.
They merge only inside the Sprint 4 product-half PR, which carries the full
33× lockstep bump to `1.9.0` and the `release-seal.json` re-seal in the same
merge — `main` then never holds a 33-skill catalog at the old number. The only
frozen interval is merge → tag (the staging eyeball, one sitting), and the
guard's refusal inside it is `missing-tag`, whose remediation already prints
the exact tag commands. The `1.8.3` frontmatter on the four skills in this
branch is build-time-only (it keeps `gen-catalog`/CI green pre-cut); the bump
rewrites it before anything merges. `OPCHAIN_ALLOW_UNTAGGED_RELEASE=1` remains
the loud escape hatch for a genuine emergency hotfix inside that interval — it
would ship `v1.9.0` untagged, so tag immediately after. (Belt-and-suspenders:
`check-release-tag.mjs` now detects the count-drift case specifically and its
refusal prints the bump-then-tag remediation instead of an empty hint.)

## 2. Boundary decisions

The four roadmap blurbs were written before parts of the current catalog
existed. Taken literally, two of them re-ship existing skills. The re-scopes:

**D1 — oc-security-hardening ≠ oc-security-auditor.** Issue #11's blurb ("a
full OWASP + threat-model pass before every deploy") describes what
**oc-security-auditor already is** — it owns `/oc-hardening`, STRIDE, OWASP
mapping, and SOC2/HIPAA *readiness mapping*. What the catalog actually lacks is
the other half: nothing **executes** the auditor's findings, and nothing runs
**mechanically before every deploy**. oc-security-hardening is scoped as the
remediation/enforcement operator: it writes the fixes (headers, staged CSP
rollout, TLS/WAF/rate-limit config as code, secrets hygiene, dependency-pinning
policy), maintains a hardening manifest (`.opchain/hardening.yaml`), and stands
the per-deploy gate that verifies the manifest. Assessment stays with the
auditor. The near-miss verb pair (`/oc-hardening` = audit the posture,
`/oc-harden` = execute the hardening) gets an explicit disambiguation line in
**both** skills' descriptions. → *Sprint 4 task: update issue #11's body to the
re-scoped mission (edit in place — votes are attached to the issue and must be
preserved).*

**D2 — oc-compliance-ops ≠ `/oc-security readiness`.** The auditor's readiness
command is a point-in-time gap analysis. oc-compliance-ops is the *standing*
operator: a control register that maps framework controls (SOC 2 CC-series,
HIPAA safeguards, GDPR articles) to concrete repo/infra artifacts, an evidence
bundle generated per deploy/release ("audit-ready docs generated at deploy
time" — the issue's own words), and policy-doc scaffolding. It consumes the
auditor's gap analysis as register input; it never re-assesses. Both skills
carry the "readiness/evidence, not certification or legal advice" disclaimer.

**D3 — oc-qa-ops ≠ oc-bug-check, ≠ oc-scale-ops.** oc-bug-check *runs* tests in
under two minutes at the commit gate; oc-qa-ops decides *which tests should
exist* (pyramid shape, coverage budgets, contract-test matrix, load-test plan).
The split the issue names ("split out of oc-bug-check") is strategy vs.
execution. Load-test *execution* (`/oc-scale loadtest`, oha/hey, perf budgets)
stays with oc-scale-ops; oc-qa-ops plans which load tests exist and what SLOs
they verify, then hands off. Contract-test *authoring* for first-party APIs
stays with oc-api-dev; oc-qa-ops places them in the pyramid.

**D4 — oc-data-ops ≠ oc-signal-forge.** Signal Forge is metric-centric: one
question → one trustworthy metric, "backend only." oc-data-ops is
estate-centric: the ingestion/transformation platform those metrics ride on
(batch/stream/CDC ingestion, staging→intermediate→marts layering, dbt project
layout, cross-pipeline data contracts with freshness/volume/schema SLAs).
Signal Forge chains *to* oc-data-ops when a metric needs a pipeline that
doesn't exist; oc-data-ops hands schema-evolution cutovers of live pipelines to
oc-migration-ops and stack choice (warehouse/queue) to oc-stack-forge.

## 3. Per-skill specs (summary — the SKILL.md files are normative)

The full contracts live in `skills/<id>/SKILL.md` (written in Sprint 1, this
branch). Summary of the load-bearing parts:

### oc-qa-ops — `/oc-qa`
- **Commands:** `pyramid` (design the test pyramid for this repo), `coverage`
  (set/revise budgets), `contracts` (contract-test matrix), `loadplan`
  (load-test plan → oc-scale-ops), `audit` (gap-audit the existing suite
  against the pyramid), `status`.
- **Mechanical output:** `.opchain/qa.yaml` — suite map + coverage budgets.
  oc-bug-check's test check reads it *when present* (absent → behavior
  unchanged; the edge is additive).
- **Chains:** in — oc-app-architect Phase 2 (authors `06-testing.md`),
  Phase 6 Evaluator (test requirements come from the budgets); out —
  oc-scale-ops (loadplan), oc-api-dev (contract authoring), oc-bug-check
  (budget consumption).

### oc-data-ops — `/oc-data-ops` (tri-agent)
- **Loop:** Designer (pipeline architecture + contracts) → Builder (dbt/ELT
  implementation) → Contract-Verifier (isolated context; replays contracts
  against built pipelines — schema, freshness, volume).
- **Commands:** `design`, `contracts`, `build`, `verify`, `observe` (wire
  freshness/volume/schema-drift monitors → oc-monitoring-ops), `status`.
- **Chains:** in — oc-app-architect Phase 2 (data-heavy discovery branch,
  parallel to the AI-app branch), oc-stack-forge (platform), oc-signal-forge;
  out — oc-monitoring-ops, oc-dash-forge (contracts feed dashboards),
  oc-migration-ops (live schema evolution).

### oc-compliance-ops — `/oc-comply`
- **Commands:** `scope` (frameworks + applicability, proportionality tiers),
  `register` (build/maintain the control register), `evidence` (generate the
  per-deploy/per-release evidence bundle), `gaps`, `policies` (scaffold/update
  policy docs), `status`.
- **Mechanical output:** `.opchain/compliance.yaml` (declared profile) +
  evidence bundles under `docs/compliance/evidence/<date>-<sha>/`. When a
  profile exists, oc-deploy-ops' gate gains a row: "evidence bundle generated
  for this deploy." Absent profile → skill inert, gate unchanged.
- **Chains:** in — oc-deploy-ops (evidence at deploy), oc-release-ops
  (compliance delta per release), oc-security-auditor (readiness gaps seed the
  register); out — oc-security-hardening (technical-control gaps →
  remediation), oc-docs-forge (policy docs ride the PR packet).

### oc-security-hardening — `/oc-harden`
- **Commands:** `baseline` (stack-aware secure baseline), `fix` (remediate a
  specific auditor finding), `csp` (staged report-only → enforce rollout),
  `gate` (install/verify the pre-deploy hardening gate), `verify` (post-fix
  verification against the live surface), `status`.
- **Mechanical output:** `.opchain/hardening.yaml` — declared controls + how
  each verifies. `/oc-harden gate` wires a project-appropriate mechanical check
  (CI step or deploy-script row). When the manifest exists, oc-deploy-ops'
  gate gains a row: "hardening manifest verifies at this SHA."
- **Chains:** in — oc-security-auditor (findings → remediation queue),
  oc-deploy-ops (gate); out — oc-security-auditor (`/oc-security compare` after
  fixes), oc-monitoring-ops (detection controls it installs get watched).
- **First dogfood target (Sprint 3):** the open HIGH finding on `POST /mcp`
  (unauthenticated checkpoint state, no TTL/size/rate limits — flagged by both
  the 2026-08-22 OSS audit §4.3 and the v1.8.3 deploy audit). v1.9 ships the
  skill *and* its first executed remediation.

## 4. Invocation-guarantee design ("ensure they get called upon")

Orchestrator §3's own measurement is the constraint: **cross-skill prose
produced zero autonomous invocations across 87 sessions.** So the design uses
four layers, from softest to hardest, and puts the load-bearing edges on the
hard ones:

**L1 — Trigger-optimized descriptions (user-initiated invocation).** Each
frontmatter `description` carries verbs + a phrase list ("design our test
strategy", "coverage budget", "dbt", "data contract", "SOC 2 evidence",
"harden this before deploy", …), ≤1024 chars, synced verbatim into
orchestrator.md §7. This is what makes the skills fire when a *user* names the
problem.

**L2 — Orchestrator edges (agent-guided routing).** skills/orchestrator.md
gains: §2 pipeline-map entries (assurance rail beside the quality gates; data
rail cross-cutting), four Upstream/Downstream rows, §3 handoff rows
(app-architect Phase 2 → oc-qa-ops at `06-testing.md` / → oc-data-ops on
data-heavy discovery; deploy audit gate → hardening + compliance rows when
their manifests exist; security-auditor findings → oc-harden), §4 smart-routing
rows, §7 descriptions, §8 facts (counts 29 → 33, tri-agent list + oc-data-ops).
One edit propagates to all 33 bundles via `npm run sync-bundles`.

**L3 — Reciprocal edits in the inviting skills** (prose alone doesn't invoke,
but absent prose *guarantees* non-invocation; these make the edges visible at
the decision point):

| File | Additive edit |
|---|---|
| `skills/oc-app-architect/SKILL.md` | Phase 2: `06-testing.md` row sourced via oc-qa-ops; a "Data-heavy branch" mirroring the AI-app branch → oc-data-ops; discovery signals for regulated data → oc-compliance-ops `scope` |
| `skills/oc-deploy-ops/SKILL.md` | Pre-deploy gate: two conditional rows — hardening manifest verifies (when `.opchain/hardening.yaml` exists), evidence bundle generated (when `.opchain/compliance.yaml` exists) |
| `skills/oc-security-auditor/SKILL.md` | "Read by" + chain line: findings hand to oc-security-hardening for execution; description gains the `/oc-hardening` vs `/oc-harden` disambiguation |
| `skills/oc-bug-check/SKILL.md` | Test check reads `.opchain/qa.yaml` when present |
| `skills/oc-scale-ops/SKILL.md` | Reads oc-qa-ops loadplan; stays execution owner |
| `skills/oc-signal-forge/SKILL.md` | NOT-line + chain: estate-level pipelines → oc-data-ops |

Round 2 of the critique loop found several of these edges one-sided and added
paired rows in eight more skills: oc-api-dev (qa-ops contract rows),
oc-code-auditor (`route: oc-security-hardening` finding tag + qa.yaml-aware
test-bootstrap), oc-dash-forge (data-contract intake), oc-integrations-engineer
(warehouse carve-out), oc-migration-ops (warehouse/dbt migrations receive
data-ops contracts), oc-monitoring-ops (data-ops monitor inventory +
`detect.*` controls), oc-release-ops (conditional compliance-delta verify
row), oc-stack-forge (Question 3b data-platform decision keys). Fourteen
existing skills carry additive v1.9 rows in total.

**L4 — Mechanical chokepoints (the edges that must hold).**
- The three `.opchain/*.yaml` activation files (two manifests + the compliance
  profile) are *data at a chokepoint*: gates that
  already run (bug-check's test step, deploy-ops' audit gate) read them when
  present. No new always-on machinery; fail-open when absent.
- Plugin: `plugins/opchain/hooks/next-suggestion.cjs` skill→command map gains
  the four skills; four `plugins/opchain/commands/<verb>.md` files register the
  slash commands.
- Deliberately **not** built in v1.9: wiring `scripts/deploy.mjs` (this repo's
  real deploy path) to any new gate. The skills instruct installing gates in
  *user* projects; opchain dogfoods via the deploy-ops SKILL.md gate rows first
  and revisits script-level enforcement after a release of lived experience.

## Appendix C — the GitHub Actions surface as a local release sequence

Deploys are manual, and this repo has precedent for Actions not firing when it
matters (the admin-merge-with-local-verification episodes). So the release
sequence does not *depend* on Actions: every workflow in `.github/workflows/`
maps to a named step in **`scripts/release-sequence.mjs`** (opchain-internal —
`scripts/` is never mirrored and is not part of the shipped skill catalog),
grouped into the three moments of a cut. `tests/release-sequence.test.js`
fails CI if a workflow is ever added without a ledger entry, and
`npm run release-sequence -- --list` prints the authoritative mapping.

| Workflow | Local step(s) | Stage | Class |
|---|---|---|---|
| `ci.yml` | checkpoint-validate, hook-suites, checkpoint-doctor, bundle-sync, skill-symlinks, unit-tests, worker-build, astro-check, roadmap-data, site-e2e | pre-merge | fail (doctor + roadmap: warn) |
| `lighthouse.yml` | lighthouse-budgets (LHCI vs local build) | pre-merge | warn |
| `release-ledger.yml` | tag-gate-expects-missing (pre-tag: the gate must refuse with `missing-tag` for exactly the new version); release-ledger (post-deploy, prod: full remote tag verification) | pre-tag + post-deploy | fail |
| `canary.yml` | canary-health (status/JSON/deny-header probe) + smoke | post-deploy | fail |
| `deploy-lag.yml` | deploy-lag (live `/api/health` version vs `origin/main`) | post-deploy | fail |
| `publish-mcp-registry.yml` | registry-publish (latest run conclusion via `gh`) | post-deploy (prod) | warn |
| `mirror-public.yml` | mirror-sync (public repo's mirror commit names the shipped SHA) | post-deploy (prod) | warn |
| `lighthouse-prod.yml` | lighthouse-prod (LHCI vs the live site) | post-deploy (prod) | warn |

Class semantics: **fail** rows gate the sequence (non-zero exit); **warn**
rows report and continue — either advisory in CI too (checkpoint-doctor) or
dependent on optional local tooling (`gh`, Playwright browsers, LHCI), each
warn-skipping with the exact install/fallback command when the tool is
absent. Invocation points: Appendix B B1 (pre-merge, on the PR branch),
B2 (pre-tag, from `origin/main`), B5 (post-deploy, staging then prod).
