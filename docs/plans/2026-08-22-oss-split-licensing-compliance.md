# opchain — public product repo, licensing, and compliance

_Decision plan, 2026-08-22. Produced by `/oc-app-architect` (boundary + options), `/oc-code-auditor` (exposure + readiness audit) and `/oc-git-ops` (split topology + runbook), as a 7-lens multi-agent sweep with an adversarial verifier per lens and a completeness critic. Every file:line below was reproduced by a verifier that did not write the finding. Full verified findings: [docs/audits/2026-08-22-oss-readiness-audit.md](../audits/2026-08-22-oss-readiness-audit.md). Analysed at `c440c7b` (main)._

_Ownership addendum, 2026-09-02: the canonical source monorepo is now
`ainatx/opchain` (immutable repository ID `1208651570`). The public product
mirror and MCP Registry identity remain `asfbay-bit/opchain-skills` and
`io.github.asfbay-bit/opchain-skills`; D2 below is preserved as the historical
2026-08-24 decision._

**The three questions, answered in one paragraph each:**

1. **Separate repo for contributors.** Invert the mirror: make `asfbay-bit/opchain-skills` (which already exists, is already the advertised install slug, and has 0 forks/PRs/issues) the *source of truth* for the product — `skills/`, `plugins/`, `.claude-plugin/`, `mcp/`, the MCP server module, the product validators/tests and the checkpoint CLI — extracted with `git filter-repo` so history is kept, then have the site repo consume it as a tag-pinned git submodule behind a top-level `skills` symlink (zero script edits). Retire the force-push mirror. Do the hygiene that every OSPO scanner checks *inside the monorepo first*, because it carries into the new repo via the history rewrite. ~1 week elapsed; ~2–3 h for the extraction itself. Don't do the "third repo + renames" variant: it rewrites 22 hard-coded slugs and the MCP-registry namespace for no functional gain.
2. **Licensing for NVIDIA-class use.** The license you have (MIT) is already acceptable to every large-enterprise allowlist. What's *not* acceptable is that the artifacts people actually download (`opchain-skills.zip`, per-skill zips, the plugin directory, `opchain.dev/LICENSE` → 404) ship **no license text at all**, the copyright holder is a GitHub handle, and there is no machine-readable license metadata anywhere (0 SPDX headers, no `license` field in either `package.json`, 0/29 `SKILL.md` declare one). Fix those regardless. The license requirement is **Apache-2.0** (decided 2026-08-22) — what NVIDIA itself ships (NeMo, TensorRT-LLM, cuda-python, container-toolkit, NeMo Agent Toolkit) and what Anthropic uses for its own open skills. Relicensing is legally clean today (one human copyright holder, zero external contributors) and effectively impossible after the first external PR, so the relicense commit lands **completely, in the monorepo, before extraction**. Pair it with **DCO sign-off, not a CLA**.
3. **Compliance.** Four different audiences get conflated under that word; each needs its own checklist (§4): (a) *outbound OSS hygiene of the repo* — SECURITY.md, SHA-pinned Actions, signed/attested releases, SBOM, Scorecard; (b) *inbound contribution* — DCO, CoC, CODEOWNERS, a second reviewer, an AI-assisted-contribution rule; (c) *the hosted service* opchain.dev — a privacy page that matches the code (it doesn't today), TTLs on KV data, a rate limit and session isolation on `POST /mcp`; (d) *adopter-side* — what an NVIDIA security reviewer checks before `/plugin install opchain`: no phone-home by default, documented hook behaviour, pinnable version, zero runtime deps (true — say so). SOC 2 / ISO 27001 apply only to the hosted service and nobody expects them of a skills repo. Export control: not subject to the EAR (published OSS, standard crypto only).

**Readiness grade today: D+.** The product tree is secret-free (verified over all 650 commits) and all-permissive; everything else is packaging, metadata and governance. Doing §2 + §3 + the §4 "must" rows moves it to a B.

### 4.6 Export control

Published open-source software using only standard cryptographic primitives (`ed25519`/`SHA-256`/`getRandomValues`) is not subject to the EAR (§734.3(b)(3)/§734.7); no §742.15(b) notification (that's for non-standard crypto source). An importer will still classify it; EAR99/not-subject is the expected outcome. OFAC is GitHub-platform-enforced.
