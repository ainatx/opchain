What's new

oc-qa-opsTest-pyramid design: coverage budgets, contract-test matrix, load-test planning. The strategy layer split out of oc-bug-check.
oc-data-opsIngestion patterns, staging → intermediate → marts layering, dbt, and data contracts replayed by an isolated Contract-Verifier.

How you'll use it

Unified app development: idea → spec → design → build with Generator/Evaluator QA loop → launch. Use for "build me an app", "I have an app idea", or any software project. Chains to oc-stack-forge and oc-ux-engineer.

Trigger with natural language or a slash command:

/oc-app/oc-discover/oc-spec/oc-design/oc-roadmap/oc-scaffold+2 more
SKILL.md≈ 14 min read
Below is the file Claude reads on invocation. It's written in the model's voice — "read this", "do that" — not a user guide. The How you'll use it section above is the one for you.

Phase 1: Discovery

Interview the user. Do not write a spec until you can state the problem in one sentence, the user in one sentence, and the non-goal in one sentence. Write the checkpoint phase: "discovery" before the first question.

// .checkpoints/oc-app-architect.checkpoint.json
{
  "phase": "discovery",
  "step": "problem-statement",
  "next_actions": ["confirm non-goal", "pick stack via oc-stack-forge"]
}

Gate: problem statement approval

Present the three sentences. Do not proceed until approved. If the user adds scope, restate all three and ask again.

CriterionWeightVerified by
Functionality40%Evaluator runs the contract's test list
Feature completeness35%Punch list coverage ≥ 90%
Code quality25%oc-bug-check passes silently

Phase 2: Stack selection

Hand off to oc-stack-forge with the problem statement and constraints. Read its handoff back before writing a line of the spec.
